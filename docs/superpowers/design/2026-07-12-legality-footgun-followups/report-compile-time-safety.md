## Ground truth from the code (what constrains the design)

- **Builders are plain-string functions.** `legal.PropAtLeast(path string, n int) Spec` just packs `Spec{Name: "propAtLeast", Args: []string{path, itoa(n)}}` (`legal/catalog_compare.go:53`). Same for the 3-path builders like `MayMoveToSlot(srcPath, dstPath, idxField string)` (`legal/catalog_stack.go:143`). `legal.Spec` is an alias for `boardgame.LegalSpec` (wire-serializable, `legal_types.go:201`), so builders must keep producing plain `[]string` args.
- **Path validation is centralized and boot-time.** `validateLegalPath` (`legal_path.go:138`) checks `Props()` maps of example readers at `NewGameManager`; `parseLegalPath` owns the 5-kind grammar. Template keys are validated at boot too (`validateLegalTemplates`/`validateLegalEmittedTemplates`, `legal_plan.go:455-461`).
- **Codegen already knows everything needed.** `boardgame-util/lib/codegen/reader.go` parses each package (via `golangAnnotations`), finds structs with the `//boardgame:codegen` doc comment, and computes `fieldsInfo` — a map of exported field name → `boardgame.PropertyType` (Int, Bool, Stack, Enum, PlayerIndex, Timer…), including fields inherited from embedded structs across packages (`typesForPossibleEmbeddedStruct`, `reader.go:222`). This is exactly the data `validateLegalPath` checks at boot, available at **codegen time**.
- **`auto.Config` already builds a fully-inflated example move.** `Config()` calls `OrphanExampleMove(throwAwayConfig)` (`moves/auto_config.go:176`) — a real, tag-inflated move instance whose `.Reader().Props()` could be consulted right there. The precondition specs are sitting in the same `config` bag under `configPropPreconditions`.
- **Suppression names are a closed set of 4 string literals** (`"inPhase"`, `"inProgression"`, `"stackConstraints"`, `"proposerIsCurrentPlayer"`), currently written as raw strings by authors (e.g. `examples/memory/tutorial_snippets_test.go:91`). No exported constants exist. [NOTE: constants shipped in the footgun batch, commit 3586f278.]
- **Go 1.22** (`go.mod`), so generics (`~string` constraints) are available.
- A caveat for any codegen/analyzer approach: **codegen is syntactic and cannot know which struct is the game state vs. player state.** Both embed `base.SubState`; only the delegate's constructors decide. Move structs *are* mechanically detectable (they embed `moves.Default`/`moves.CurrentPlayer`/etc. from the `moves` package, which codegen already resolves). Also note `structConfig` (`reader.go:279`) silently ignores unknown magic-comment arguments, so extending the *existing* comment's argument list must not collide with `reader|readsetter|all`.

## Proposal 1 (codegen path constants) — RECOMMEND, top pick

### Phase 1: untyped string constants, zero framework change

Teach codegen to emit an `auto_paths.go` alongside `auto_reader.go`. For kind, use a new dedicated magic comment (safer than overloading `boardgame:codegen`'s argument, which silently no-ops on unknown args):

```go
//boardgame:codegen
//boardgame:legalpaths game
type gameState struct { ... }

//boardgame:legalpaths player
type playerState struct { ... }

// move structs need no annotation: codegen detects the embedded
// moves.* type it already resolves for reader generation.
```

Generated (for memory):

```go
// auto_paths.go — generated by boardgame-util codegen. DO NOT EDIT.

// Paths for gameState (kind: game).
const (
	pathGameHiddenCards  = "game.HiddenCards"
	pathGameVisibleCards = "game.VisibleCards"
	pathGameNumCards     = "game.NumCards"
	// ...
)

// Paths for playerState (kind: player). players[*] variants too:
const (
	pathPlayerCardsLeftToReveal     = "player.CardsLeftToReveal"
	pathPlayersAllCardsLeftToReveal = "players[*].CardsLeftToReveal"
)

// Paths for moveRevealCard (kind: move).
const (
	pathMoveRevealCardCardIndex = "move.CardIndex"
)
```

Author-facing before/after:

```go
// before
legal.PropAtLeast("player.CardsLeftToReveal", 1)
legal.MayMoveToSlot("game.HiddenCards", "game.VisibleCards", "move.CardIndex")

// after — zero signature changes anywhere
legal.PropAtLeast(pathPlayerCardsLeftToReveal, 1)
legal.MayMoveToSlot(pathGameHiddenCards, pathGameVisibleCards, pathMoveRevealCardCardIndex)
```

Untyped `const` strings assign to `string` parameters with no conversion, so **the `legal` package doesn't change at all**. Wins: a typo is now an *undefined identifier* (compile error, red squiggle in any editor via gopls — genuinely earlier than `go test`); autocomplete; and renaming a state field + re-running codegen makes every stale path a compile error. Struct names are lowercase (`gameState`), so constants are package-private — fine, since `ConfigureMoves` lives in the same package.

Cost: ~300–500 LOC in `boardgame-util/lib/codegen` (one new template, magic-comment parsing, kind detection for moves via the already-resolved embedded-type info, tests). No compat risk: raw strings keep compiling forever; games that never re-run codegen are unaffected.

### Phase 2 (optional): typed paths + method sugar

Add distinct types in `legal` with predicate methods hanging off them, ent-style:

```go
// package legal (new, additive)
type IntPath string
type BoolPath string
type StackPath string

func (p IntPath) AtLeast(n int) Spec        { return PropAtLeast(string(p), n) }
func (p IntPath) Compare(op string, n int) Spec { return PropCompare(string(p), op, n) }
func (p BoolPath) IsTrue() Spec             { return PropEquals(string(p), "true") }
```

Codegen emits `var` structs instead of consts (constants can't be struct fields):

```go
var gamePaths = struct {
	HiddenCards  legal.StackPath
	VisibleCards legal.StackPath
	NumCards     legal.IntPath
}{"game.HiddenCards", "game.VisibleCards", "game.NumCards"}

var playerPaths = struct{ CardsLeftToReveal legal.IntPath }{"player.CardsLeftToReveal"}
```

Author-facing:

```go
moves.WithPreconditions(
	playerPaths.CardsLeftToReveal.AtLeast(1).WithMessage("reveal.no_cards_left"),
	legal.RevealableCardAt(gamePaths.HiddenCards, gamePaths.VisibleCards, movePaths.RevealCard.CardIndex),
)
```

This adds **property-type** safety (`.AtLeast` only exists on `IntPath`) on top of existence safety. For the multi-path builders, either add typed overload names, or make the existing builders generic — `func RevealableCardAt[S, D ~string, I ~string](src S, dst D, idx I) Spec` — which is source-compatible for every existing raw-string call site (one obscure exception: taking a func *value* like `f := legal.PropAtLeast` would need instantiation; nothing in the repo does this). Cost: ~200 LOC in `legal` + touching ~20 builder signatures + codegen template variant. The `players[move.Field].Prop` grammar composes via a helper: `func PlayersBy(field IntPath, prop ...)` or a `movePaths.X.PlayerOf(...)` method — design it when needed.

**Verdict: recommend Phase 1 unconditionally; Phase 2 is a nice follow-on but Phase 1 alone captures ~90% of the value (typo → compile error) at ~10% of the cost.** This is the sqlc/ent/sqlboiler idiom: the tool that already understands your schema emits the identifiers, and hand-typed strings become opt-in legacy.

## Proposal 2 (Config-time validation of `move.*` paths) — MAYBE, low priority

Feasible today: inside `Config()` (`moves/auto_config.go:154`), after `OrphanExampleMove` succeeds, read `config[configPropPreconditions].([]legal.Spec)`, walk each spec's args that parse as `move.*` paths, and check them against `generatedExample.Reader().Props()`. `MustConfig` then panics *at the exact `ConfigureMoves` call site* with a stack trace, instead of the boot gauntlet's (already move-named) error.

But honestly priced: `ConfigureMoves` runs *during* `NewGameManager`, so this fires in the **same `go test` run, milliseconds earlier**, with only marginally better locality. It also has a smell: `Config` would need to know which arg positions are paths (predicate arity knowledge lives in the registry, not in `moves`), or it heuristically scans all args for a `move.` prefix — workable but a second, weaker copy of validation logic. `game./player.` paths can't be safely checked here (no guaranteed example state mid-setup); the boot gauntlet already owns that.

**Verdict: maybe — only as a cheap heuristic (`strings.HasPrefix(arg, "move.")` → check `Props()`), and only if error-locality complaints actually arise. It does not deliver a new failure *class* earlier; Proposal 1 does.**

## Proposal 3 (template keys) — RECOMMEND the colocated-declaration idiom

Today's typo surface is the *pairing*: the key appears once in `WithMessage("reveal.no_cards_left")` and once in `ConfigureLegalTemplates()` (`examples/memory/main.go:317,365`); boot validation catches mismatches, but only at test time. Three tiers:

- **Tier 0 (free, documentation only):** teach the tutorial to declare a shared package constant used at both sites. Kills the mismatch class at compile time with zero framework change. Should happen regardless.
- **Tier 1 (recommended): colocated declaration.** Add an optional body to the spec:

  ```go
  // package legal
  func (s Spec) WithMessagef(key, body string) Spec  // sets Message=key, MessageBody=body
  ```

  `LegalSpec` gains `MessageBody string` with `json:"-"` (stripped from the wire ledger; bodies ship via the existing template-table channel). Plan assembly at boot overlays collected bodies onto `DefaultTemplates()` before `ConfigureLegalTemplates` overrides (delegate keeps last word for i18n/overrides). Author-facing:

  ```go
  legal.PropAtLeast(pathPlayerCardsLeftToReveal, 1).
  	WithMessagef("reveal.no_cards_left", "You have no cards left to reveal this turn"),
  ```

  and `ConfigureLegalTemplates` disappears for the one-off case entirely — the whole mismatch class becomes unrepresentable. Cost: small (~100 LOC: field, method, boot overlay, tests); fully backward compatible (`WithMessage` unchanged).
- **Rejected variant:** auto-deriving the key from the body (`WithMessagef("You have no cards left")` alone). A key hashed/derived from English text changes whenever copy is edited, breaking localization, greppability, and the wire contract — the spec's whole reason for keys-not-strings (`legal_types.go:113`).

Keep explicit keys; just declare the body next to them.

## Proposal 3b (suppression names) — RECOMMEND, trivial [SHIPPED in footgun batch, 3586f278]

Export constants in `moves` (or typed `type ContributedPrecondition string` accepted by a `~string`-generic `WithoutPrecondition`):

```go
const (
	PreconditionInPhase                 = "inPhase"
	PreconditionInProgression           = "inProgression"
	PreconditionStackConstraints        = "stackConstraints"
	PreconditionProposerIsCurrentPlayer = "proposerIsCurrentPlayer"
)
```

Untyped consts → `WithoutPrecondition(string)` signature untouched, raw strings still work. It's a closed framework-owned set of 4; there is no reason authors should ever type these. Cost: ~20 LOC + doc updates.

## Proposal 4 (go vet analyzer) — REJECT for now

A `golang.org/x/tools/go/analysis` analyzer *could* statically resolve `legal.PropAtLeast("player.X", …)` string literals against the player-state struct: with full type info it can find the delegate's `GameStateConstructor`/`PlayerStateConstructor` return types (or the `concreteStates` casts) and check field existence/type. But:

- It duplicates the grammar + `Props()` semantics (including tag-based inflation like `sizedstack:"cards,40"` and embedded behaviors) that `validateLegalPath` already checks — a second implementation that will drift.
- `TestManager` already turns every one of these typos into a `go test` failure; the only marginal gain is editor-time feedback, which **Proposal 1 delivers more cheaply and more robustly** (undefined identifier beats a custom analyzer).
- Distribution friction is real: gopls only runs custom analyzers via a custom gopls build or `vettool` wiring; `boardgame-util vet` would exist but people must remember to run it — strictly worse than "the code doesn't compile."
- It can't check dynamic paths (string concatenation), and once Proposal 1 lands, literal paths become the legacy minority.

Fair prior art exists (`printf` format-string checking, `structtag`), so it's feasible — just dominated. Revisit only if a large body of raw-string call sites persists post-codegen.

## Proposal 5 (prior art)

- **ent** is the closest model: generated per-entity predicate packages (`user.AgeGTE(18)`) = Proposal 1 Phase 2 exactly. Its lesson: generate *values with methods*, not just strings, and keep an escaping hatch (`sql.P`) for raw access — mirrored here by raw strings staying legal.
- **sqlc / sqlboiler**: schema-derived typed identifiers (`models.UserColumns.Age`) = Phase 1; validation happens at generation time, runtime accepts anything.
- **protobuf**: generated enum constants + a stable wire format underneath — validates the "typed sugar over stringly wire format" layering already chosen for `LegalSpec`.
- **stringer/go:generate**: the delivery mechanism already in place (`//go:generate boardgame-util codegen`); adding a second emitted file (`auto_paths.go` next to `auto_reader.go`, precedent: `auto_enum.go`) is idiomatic.
- **wire**: compile-time DI; less applicable — its lesson (fail at build, not at run) is already the thesis here.

---

## Top 2 recommendations, ranked

1. **Codegen-emitted path constants (Proposal 1, Phase 1 first).** Codegen already computes exactly the field→PropertyType map boot validation checks; emitting untyped `const` path strings into `auto_paths.go` moves the dominant typo class (property paths, all five grammar kinds) from test time to compile time with **zero change to the `legal` package** and perfect backward compatibility. Phase 2 (typed `IntPath`/`StackPath` + method builders, generic `~string` acceptance) as a follow-on for property-*type* safety.
2. **Colocated template declaration (`WithMessagef(key, body)`, Proposal 3 Tier 1) + exported suppression constants (3b).** Together these eliminate the remaining two string surfaces: the key/table mismatch becomes unrepresentable (the body lives on the spec; boot overlays it into the table), and the closed 4-name suppression set becomes framework-exported constants. Both are small, additive, and keep raw strings working.

Skip the vet analyzer; treat Config-time `move.*` validation as an optional polish item only if boot-error locality proves annoying in practice.
